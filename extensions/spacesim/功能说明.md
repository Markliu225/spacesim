# spacesim 功能说明（中文版）

> English version: see [README.md](README.md).
> 函数级深度文档：[`docs/系统概览.md`](docs/系统概览.md)
> Function-level deep dive：[`docs/TECHNICAL_REPORT.md`](docs/TECHNICAL_REPORT.md)

在 Hypatia (Kassing et al., IMC 2020) 之上做 **LLM-on-satellite**
仿真。把 satgenpy 拓扑生成、ns-3 `llm-workload` C++ 模块、Azure
trace 流量生成器、和一个 Streamlit Dashboard 整合成一个一致的代码库。

仿真器是真包级别（TCP 端到端）。从地面站建连，经过 ISL 多跳，到一个
FIFO 队列的推理 SAT，再原路返回 FIN，每一跳链路都建模了带宽、排队和
TCP 分段。

## 三、两种工作负载模式

由 `WorkloadConfig.source` 切换，对应侧栏 Workload source 单选。

### 3.1 合成（`source = "synthetic"`）

每个 GS application 在 ns-3 里跑一个 lazy 链：
inter-arrival ~ Exponential(1/λ)，L_in ~ Normal(μ, σ²) clamped 到
[L_in_min, L_in_max]。schedule 写出**老的 15 列 CSV**。适合"如果速率
翻倍会怎样"这种参数扫描，不用重新生成数据。

### 3.2 trace 回放（`source = "trace_replay"`）

`extensions/traffic_generator/traffic_gen.py` 提前生成的每个 GS 的
events CSV 被 stage 进 run dir，里面每一条 `t_emit_ns` 和 `L_in`
都来自真实 Azure 数据。schedule 写出**新的 16 列 CSV**，末列指向
events 文件路径。C++ 侧 `LLMRequestApplication::ScheduleEventsFromFile()`
在 StartApplication 时全部 Schedule 进队列。

`install_events_replay` 做了三件你需要知道的事：

1. **截断 + 平移**：只保留落在
   `[trace_start_offset_sec, trace_start_offset_sec + duration_seconds)`
   区间的 event，并把 `t_emit_ns` 减去 offset，让窗口内第一条 event
   对齐 sim t=0。**这是必须的**——不然 ns-3 会把 trace 的 24 小时
   ~325 万条事件全 schedule 进队列，仿真窗口 30s 也只能跑 0.03%，
   剩下都被静默切掉但占了内存。
2. **吐出 fit 摘要**（`{events_total, events_kept, kept_fraction, per_gs}`），
   dashboard 在你点 Run **之前**就会显示"X 条会触发 / Y 条总数"。
3. **GS 按 idx 对齐**：拓扑里 N 颗卫星 + M 个 GS 时，trace 里
   gs_idx 0..M-1 直接映射到节点号 N..N+M-1；多出来的（gs_idx ≥ M）
   带警告跳过——所以 10 城 trace 能安全驱动 5 城拓扑。

## 四、地面站

两种声明方式，侧栏单选切换：

| 模式 | 来源 | 何时用 |
|---|---|---|
| Preset | Hypatia 自带的 top-100 城市文件，`gs_set ∈ {top_5_cities, top_20_cities, top_100_cities}` 取前 N 个 | 快速实验；可复现 baseline |
| 自定义 JSON | 用户文件，格式同 `traffic_generator/ground_stations.json`：一个 list of dict，至少要有 `name / lat / lon`（也可包含 `gs_idx`、`peak_lambda`、`elevation_m`） | 自定义城市列表；让 trace 生成和拓扑共享同一份 GS 源 |

启用自定义 JSON 时，`topology_hash()` 会把文件内容的 SHA-1 算进去——
换 GS 列表 = 不同 hash = 触发拓扑重生成（这是正确的）。
`_select_gs_basic_subset` 把两种来源都翻译成 Hypatia 的
`<id>,<name>,<lat>,<lon>,<elev>` 格式。预览 globe 用的
`_load_gs_records` 读同一份源，所以 3D Tab 看到的 GS 位置就是仿真
真实放置的 GS 位置。

## 五、长时间仿真（1h、2h 等）

侧栏 Duration 现在有两档：

- **short**（5–600 秒）：适合 trace 短片段、速率扫描
- **long**（1–120 分钟）：适合日变趋势、handover 研究

duration 加长时必须把 `update_interval_ms` 也调大，让 fstate 文件数
保持在量级内。schema validator 把上限设在 **5000 个 fstate 文件**，
超了会拒绝并建议合适的 interval：

```
3600 s × 100 ms = 36 000 个文件   ← 被拒
3600 s × 5000 ms = 720 个文件     ← OK
```

侧栏会在你点 Run **之前**显示一个墙钟预估（`~N 秒`），公式是
"30s 仿真 trace replay 大约 10s 墙钟"加上每个 fstate 的 IO 开销。
实测：1h trace replay × 10 城市约 **20 分钟墙钟**；2h 约 **40 分钟**。

## 六、动态 3D 球

3D Globe Tab 现在有一个**时间滑块**，实时重新传播星座：

- 卫星位置：开普勒解析传播
  （`mean_motion = √(μ/a³)`），然后惯性系反向旋转 `−ω⊕ · t` 转到
  ECEF（这样地球看上去静止，卫星在转）。
- ISL：`+Grid` 邻居（同平面相邻 + 跨平面下一面；去掉 Walker-Star
  seam 环绕，再用"弦中点 < 地球半径就丢"做一道哨兵）。
- GSL：每个 GS 取仰角 > `min_elevation_deg` 的最近卫星。时间往前推，
  绿色 GSL 线会从一颗卫星跳到下一颗——直接看见 handover 发生，
  和仿真器从 fstate 文件读到的 GSL 切换在 1-2 个 update interval
  内一致。

可视化证据在 [`docs/dynamic_proof/`](docs/dynamic_proof/)：

- `three_frame_evidence.png` —— t=0、1500s、3000s 三帧 2D 世界地图，
  刚 handover 的 GSL 标红
- `evidence_composite.png` —— 6 帧世界地图 + 50 分钟 30 秒粒度的
  "每个 GS 当前连到哪颗卫星"轨迹图

实测 Walker-Star 10×10 @ 550 km、10 个城市的 `ground_stations.json`：

```
50 分钟 × 10 GS × 30 秒粒度 → 共发生 92 次 handover
每对 (GS, 卫星) 平均维持 ≈ 326 秒 ≈ 5.4 分钟
```

5.4 分钟正好对应 Starlink 级卫星从地平线升起到落下的可见窗口——
模型在物理上是对的。

## 八、两个不能改的契约

1. **`satellite_roles.txt`** —— 每行 `<sat_id>,<C|T>`。
   `topology-satellite-network.cc` 的 C++ patch 在仿真启动时读它，
   把 C SAT 加进 `m_endpoints` 集合，让 schedule reader 接受
   SAT-as-endpoint。由 `topology/roles.py::write_roles` 写，
   `LlmWorkloadScheduler` 和 fstate 增强器都会读。

2. **LLM 日志格式** —— ns-3 模块产生三族 CSV，由
   `analysis/lifecycle.py` JOIN：

   - `llm_gather_node<sat>.csv` —— 每个 SAT 的 prompt 收集事件
     （`t_first_arrival_ns`、`t_last_arrival_ns`、`D_gather_ns`、
     `src_node_id`、`L_in`、`t_emit_ns`）。
   - `llm_compute_node<sat>.csv` —— 每个 SAT 的推理事件
     （`t_queue_enter_ns`、`t_compute_start_ns`、`t_compute_end_ns`、
     `T_compute_ns`、`T_queue_wait_ns`、`L_in`、`L_out`）。
   - `llm_response_node<gs>.csv` —— **每条请求两行**：
     `response_pkt_id=0`（第一字节到达）、`response_pkt_id=1`
     （最后字节到达）。`build_lifecycle_df` 的 min/max group-by 同时
     还原 TTFT 和 total，不用改 parser。

   JOIN key：gather × compute 用 `(req_id, compute_sat_id,
   src_node_id, L_in)`；和 response 再用
   `(req_id, src_node_id == gs_node_id)`。复合键避免不同 GS 之间
   req_id 冲撞。

## 九、传输层：全 TCP 端到端

- 每条 LLM 请求开**一个新的** TCP 套接字 GS → compute SAT。
- 流头 24 字节是 `LLMHeader`
  （`t_emit_ns`/`req_id`/`src_node_id`/`L_in`/`reserved`）；
  紧接 `L_in × bytes_per_token` 字节 prompt payload。GS 侧
  `ShutdownSend` 信号 prompt 结束。
- `GatherApplication` 收齐 header + payload，回调把 socket 交给
  `ComputeApplication`。
- `ComputeApplication` 把请求入队，FIFO 处理。服务时间
  `T_compute = α·L_in + β·L_out + γ`（纳秒）。L_out 由 compute SAT
  自己采样（`Normal(LOutMean, LOutStd²)` clamp 到 `[LOutMin, LOutMax]`）。
- 响应走**同一个** TCP socket 回来；SAT 半关闭后 GS 看到 FIN，
  写两行（`response_pkt_id ∈ {0, 1}`）到 response 日志。

所以 `T_uplink_ns` **包含** TCP 三次握手（~1 RTT）和大 prompt 的
慢启动爬升——这些都是仿真器一等公民。

## 十一、已知约束

1. **`max_isl_length_m`** 设成 `2·(R⊕+h)·0.99`（轨道直径上限），不是
   经典的 ~5 016 km 大气层下限。ISL 不保证清出 80 km 大气——dashboard
   实验语义下没问题，做生产级 RF 研究要重新评估。见
   `topology/build.py::_max_isl_length_m`。
2. **satgenpy 需要 ≥ 10 个 fstate 时间步**。我们用清晰的错误信息拒绝
   不达标的配置。
3. **fstate 是逗号严格的**。ns-3 parser 做 `split_string(",", 5)`，
   任何分不到 5 字段的行（如 `#` 开头注释）会 abort。
   `fstate_augment.py` 不写注释；它用旁路文件
   `.phase_a_augment.json` 记 augmented 的 `(dst, t)` 对。
4. **`req_id` 是 per-source-GS 的，不是全局**。`build_lifecycle_df`
   用复合 JOIN（见第八节）规避了冲撞。
5. **Dashboard 3D 球用开普勒，不是 SGP-4**。仿真器内部用 satgenpy
   的 SGP-4。视觉上一致，但 24 小时尺度的滑块和真 SGP-4 会差几度。
6. **只支持单 shell**——schema 是 list，但 `generate_topology` 只
   materialize `shells[0]`；多 shell 会警告并丢弃。
7. **L_out 由 Compute 采样，不读 trace**。即便是 trace 回放，
   `ComputeApplication` 还是从 `Normal(LOutMean, LOutStd²)` 采样
   L_out。trace 的 `L_out` 列被解析但**目前没用**。技术报告里列为
   roadmap。
8. **ns-3 收尾 SIGIOT**。ns-3 在 teardown 有个空指针解引用，
   发生在 `STORE LLM WORKLOAD RESULTS` 完成之后。日志已经全部写完。
   Dashboard 把 `rc≠0 + llm_workload_summary.csv 存在` 当作成功。

## 十二、历史

这个包是三个前置模块的整合：

- **Phase A** —— compute 卫星作为合法流量端点。
  `topology-satellite-network.cc` 的 C++ patch、`satellite_roles.txt`
  契约、`fstate_augment.py` 都源于此。
- **Phase B** —— C++ `llm-workload` ns-3 应用模块（仅请求 + sink，
  没有返回路径）。
- **Phase C** —— 完整 LLM 请求生命周期：gather + compute + response。

整合之后的新增功能：

- **Azure trace 整合**（`traffic_generator/`、`events_replay.py`、
  16 列 schedule、`LLMRequestApplication::ScheduleEventsFromFile`）。
- **自定义 GS 列表**（`gs_config_path` 字段，JSON 驱动的拓扑）。
- **长时间仿真支持**（slider 60 s → 7200 s，fstate 数量护栏）。
- **动态 3D 球**（时间滑块 + 开普勒传播 + GSL handover 可视化）。
- **Cache 部分命中**（只 `(duration, interval)` 变时只重生 dynamic
  state；TLE/ISL 复用）。

各阶段工作日志、result.md、老 README 都保存在
[`docs/history/`](docs/history/)。

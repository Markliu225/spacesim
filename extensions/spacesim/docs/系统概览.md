# spacesim 系统概览（中文版）

这份文档的目标：**让你按数据流从头读到尾、读完就知道每一块在做什么、当前到底能不能用**。
英文版的逐函数报告在同目录 `TECHNICAL_REPORT.md`；这份是中文整理版，强调"输入→输出→当前状态"。

读完这份文档你应该能回答：
- 一个 LLM 请求从地面站发出，到收到第一个响应字节，**中间经过哪几个文件、哪几个进程**？
- 我想换一个工作负载来源（合成 vs Azure trace），**改哪里**？
- 我想换一个星座（500 km vs 1200 km），**改哪里**？什么会被缓存复用？
- 仿真跑完之后，**结果落在哪儿**？分析脚本读的是什么？

## 1. 流量生成器：`traffic_generator/`

**这一步是什么？** 把真实的 Azure LLM Inference Trace 转成"每个城市自己的请求时间表"。是**离线一次性**的工作——生成一次可以反复喂给仿真器跑很多次。

### 1.1 输入

- **Azure trace CSV**：`AzureLMMInferenceTrace_multimodal.csv`（约 34MB，1 周，1M 行）。我们只用三列：`TIMESTAMP`、`ContextTokens`、`GeneratedTokens`。
  - 已经下载在 `traffic_generator/azure_trace/`。
  - 如果没有，脚本会自动造一份合成 trace（同样的列名，高斯日峰形）。
- **GS 配置 JSON**：`traffic_generator/ground_stations.json`，10 个城市，字段 `gs_idx / name / lat / lon / peak_lambda`。
  - 默认 `peak_lambda = 10.0 req/s`（每个 GS 一天中的最高那一小时的请求速率）。

### 1.2 内部做了什么（按顺序）

1. **拟合 (`trace_fitter.py`)**：把整个 Azure trace 按"小时-of-day" 分桶 (`d[24]`)，每桶里塞一堆该小时观察到的 `(L_in, L_out)` 对。归一化后 `d[τ]` 就是 0~1 之间的日内变化曲线，峰值=1。
2. **本地时区平移**：每个 GS 用它的经度算"它当地的小时-of-day"：
   `τ = (utc_sec/3600 + lon/15) mod 24`
   这样 Tokyo 的本地高峰落在 UTC 早上，纽约的高峰落在 UTC 下午——和真人活动节律对得上。
3. **NHPP thinning (`nhpp_generator.py`)**：用 Lewis-Shedler 算法生成符合速率 `λ_peak · d(τ)` 的事件时刻。
   - 先估计上界 `λ_max ≈ 1.1 × max(λ(t))`。
   - 按速率 `λ_max` 生成候选事件（指数间隔）。
   - 每个候选以概率 `λ(t)/λ_max` 接受。
4. **采样 L_in / L_out**：每接受一个事件 `t`，从 `d[floor(τ)]` 那个桶里**随机抽一对**真实的 `(L_in, L_out)`。
   - 用经验采样而不是 KDE，因为长尾里偶尔有 8k+ token 的 prompt，KDE 会把它们抹平到不合理的范围。
5. **写盘**：每个 GS 一份 CSV，列是 `req_id, src_gs_idx, t_emit_ns, L_in, L_out`。req_id 是**GS 本地**的 0..N-1。

### 1.3 输出

```
traffic_generator/real_run/
├── per_gs/
│   ├── events_gs0_tokyo.csv         (~650k 行/24h)
│   ├── events_gs1_delhi.csv
│   ├── events_gs2_shanghai.csv
│   ├── events_gs3_sao_paulo.csv
│   ├── events_gs4_mumbai.csv
│   ├── events_gs5_mexico_city.csv
│   ├── events_gs6_beijing.csv
│   ├── events_gs7_osaka.csv
│   ├── events_gs8_cairo.csv
│   └── events_gs9_new_york.csv
├── diurnal_shape.png       (d(τ) 24小时曲线)
├── per_gs_hourly.png       (每个 GS 每小时请求数)
└── generator_report.md     (汇总报告)
```

**`t_emit_ns` 是什么？** 仿真器内部的"GS 在这个纳秒发起这条请求"。t=0 对应 UTC 午夜。也就是说 Tokyo 在 t=8h（UTC 8 点 = JST 17 点）才进入它的高峰期。

### 1.4 命令行用法

```bash
cd hypatia/extensions/traffic_generator
python traffic_gen.py \
    --azure-trace azure_trace/AzureLMMInferenceTrace_multimodal.csv \
    --gs-config ground_stations.json \
    --duration-sec 86400 \
    --output-dir real_run \
    --report
```

`real_run/` 已经生成过了，可以直接复用。

✅ **能用**。10 个城市 × 24h 已经生成完，每个 GS 大约 65 万条事件，总计约 650 万条。
✅ 仿真器侧已经支持直接读这些文件（trace_replay 模式，下面讲）。

## 2. 参数配置：`spacesim/config/schema.py`

**这一步是什么？** 把所有"用户能拨的旋钮"装进一个 dataclass。dashboard 的侧栏、scenario 脚本、缓存系统都依赖这个 schema 作为唯一接口。

### 2.1 四个子配置

#### `ShellConfig` — 星座形状

| 字段 | 默认 | 含义 |
|---|---|---|
| `altitude_km` | 550 | 卫星高度 |
| `inclination_deg` | 53 | 轨道倾角 |
| `num_planes × sats_per_plane` | 10×10 | Walker-Star 网格 |
| `phase_offset` | 0 | 相位偏移 F |
| `min_elevation_deg` | 25 | GS 看卫星的最小仰角 |
| `isl_pattern` | `"+Grid"` | ISL 连法（前后±1 + 左右±1） |
| `compute_ratio` | 0.10 | 多少比例的卫星是 compute (C) |

#### `WorkloadConfig` — 流量

**这里 trace_replay 集成是最近加进来的**，重点说明：

| 字段 | 默认 | 含义 |
|---|---|---|
| `gs_set` | `"top_5_cities"` | 拓扑里放几个 GS：5 / 20 / 100 |
| **`source`** | `"synthetic"` | **`synthetic`（用 Poisson+Normal 现采）或 `trace_replay`（读 events CSV 回放）** |
| **`trace_per_gs_dir`** | `""` | 回放模式下指向 traffic_generator/real_run/per_gs |
| **`trace_stage_mode`** | `"copy"` | `copy`（拷进 run_dir，安全）或 `symlink`（软链，省空间） |
| **`dst_strategy`** | `"first_compute"` | 每个 GS 选哪个 C SAT：`first_compute`（全部打到最小 ID 的 C SAT）或 `per_gs_round_robin`（轮流分配） |
| `lambda_total` | 10 | 总速率 req/s，**只在 synthetic 模式生效** |
| `L_in_{mean,std,min,max}` | 500/100/1/2000 | prompt token 数分布；replay 模式下 mean/std 被忽略，min/max 仍然是 clamp |
| `L_out_{mean,std,min,max}` | 200/50/1/1000 | 响应 token 数分布；**两种模式都生效**（Compute 自己采样 L_out） |
| `bytes_per_token` | 4 | 每个 token 多少字节 payload |
| `packet_payload` | 1400 | 旧 Phase B UDP 残留字段，TCP 路径用不上 |

#### `ComputeConfig` — LLM 推理成本

`T_compute = α · L_in + β · L_out + γ`

| 字段 | 默认 | 含义 |
|---|---|---|
| `alpha_ns_per_input_token` | 100 µs/tok | prefill 系数 α |
| `beta_ns_per_output_token` | 50 µs/tok | decode 系数 β |
| `gamma_ns` | 10 ms | 固定开销 γ（模型 load、KV cache warmup） |

#### `SimulationConfig` — 仿真窗口

| 字段 | 默认 | 含义 |
|---|---|---|
| `duration_seconds` | 30 | 仿真总时长 |
| `epoch_iso` | `2024-01-01T00:00:00Z` | sim t=0 对应的 UTC 时刻（SGP-4 用） |
| `update_interval_ms` | 1000 | fstate 路由表更新间隔；越小越精确但生成的 fstate 文件越多 |

### 2.2 关键方法

- `to_json()` / `from_json()` — Save/Load 配置用，宽松解析，未知字段忽略。
- `topology_hash()` — 只哈希 `shells`，**不哈希 workload/compute/simulation**，所以改流量参数不会触发星座重生成（缓存复用）。
- `validate()` — 在 dashboard 点 Run 之前过一遍，返回人类可读的错误列表；
  - synthetic 模式校验 `lambda_total > 0`；
  - **trace_replay 模式校验 `trace_per_gs_dir` 是真实存在的目录**；
  - 两种模式都校验 `L_in_min ≤ L_in_max` 等。

✅ schema 完整，dashboard / scenario / 缓存三方都接通了。
✅ trace_replay 字段刚加上，JSON 往返、validation 都过了。

## 3. 拓扑生成：`spacesim/topology/build.py`

**这一步是什么？** 拿 `ShellConfig` + `gs_set`，调 satgenpy 生成一个 LEO 星座的全部静态/动态文件，并标好哪些卫星是 compute、哪些是 transit。

### 3.1 输入

`generate_topology(config, cache_dir, on_progress=None)` 的入参：
- `config: ExperimentConfig`（只读 `shells` 和 `workload.gs_set` 和 `simulation`）。
- `cache_dir: Path`（默认 `spacesim/cache/`）。
- `on_progress`：进度回调（dashboard 用来推 live log）。

### 3.2 缓存机制

第一步先看 `cache/<topology_hash>/.dashboard_topology_ok` 这个 sentinel 文件存不存在。
- 存在 → 命中缓存，直接读 `TopologyResult` 返回，**整个第 3 节跳过**。
- 不存在 → 走完整生成流程。

因为 `topology_hash` 只哈希 shells，所以**只要你不改 altitude/inclination/num_planes/sats_per_plane/phase_offset/min_elevation/isl_pattern/compute_ratio，就永远命中缓存**。改流量参数、改 L_in、换 trace、换仿真时长——都不会触发重生成。

### 3.3 生成流程（缓存未命中时）

按 `paper/satellite_networks_state/main_starlink_550.py` 的套路调 satgenpy：

1. **TLE** — 生成 `tles.txt`：每个卫星一组 TLE，平面对应 RAAN 均匀分布。
2. **ISL** — `+Grid` 连法：每颗卫星 4 个邻居（前后同平面 ±1 + 跨平面 ±1）。`isls.txt`。
3. **GSL 接口** — 读 `paper/.../ground_stations_cities_sorted_…_top_100.basic.txt`，取前 5 / 20 / 100 个城市。每个 GS 一个 GSL 接口。`gsl_interfaces_info.txt`、`ground_stations.txt`。
4. **动态转发状态 (fstate)** — 用 Hypatia 的 `algorithm_free_one_only_over_isls`：每 `update_interval_ms` 生成一份 `fstate_<t_ns>.txt`，里面是当前时刻所有节点对的下一跳。这是路由的**真实来源**。
5. **角色标注 (`roles.py`)** — 调 `assign_by_plane(num_planes, sats_per_plane, compute_planes)`，把整条平面标成 C：
   - `compute_planes` 由 `_assign_compute_planes(N_P, ratio)` 算出来：均匀间隔挑 `ceil(ratio × N_P)` 个平面。
   - 默认 ratio=0.10、10 平面 → 选平面 0 → sat 0..9 全是 C。
   - 写到 `<cache>/satellite_roles.txt`，每行 `<sat_id>,<role>`。
6. **fstate 增强** — 默认的 fstate 只包含"sat → GS"的下一跳。但我们的请求是"GS → SAT"（compute SAT 作为目的地）。所以要为每个 C SAT 补一份"路由表的目的地包含这颗 SAT"。
   - 对每个 C SAT 跑 `paper/satellite_networks_state/fstate_augment.py`，重写所有 `fstate_<t>.txt`。
   - 记一个 `.phase_a_augment.json` manifest 记录"已经为哪些 dst sat 补过了"。
   - **没有这一步，GS→C 的 TCP 包会在第一跳被丢弃。**

### 3.4 输出 (`TopologyResult` dataclass)

```python
TopologyResult(
    state_dir=Path("cache/<hash>/state/dashboard_h550_i53_n10x10_2af946"),
    dynamic_state_dir=Path(".../dynamic_state_1000ms_for_30s"),
    roles_path=Path("cache/<hash>/satellite_roles.txt"),
    num_satellites=100,
    num_ground_stations=5,
    cache_hit=True / False,
)
```

dashboard 拿到这个就有了"state 目录的路径"和"GS 数量"两个关键信息。

✅ 完整、稳定。Phase A 时期就跑通了。
✅ 缓存命中后第二次起秒过。

## 4. 调度文件生成：`schedule.py` vs `events_replay.py`

**这一步是什么？** 把"哪个 GS → 哪个 C SAT、用什么参数、什么时间发"写成一行行 CSV。ns-3 启动后用这个 CSV 去 install application。

### 4.1 三种 CSV 列数

| 列数 | 谁会写 | 谁会读 | 含义 |
|---:|---|---|---|
| 11 | 旧的 Phase B 脚本 | C++ schedule reader | 兼容历史 fixture，不再使用 |
| **15** | `schedule.generate_schedule()` | C++ reader | **合成模式**：用 Poisson(λ) + Normal(L_in) 现采 |
| **16** | `events_replay.install_events_replay()` | C++ reader | **回放模式**：最后一列 `events_filename` 指向那个 GS 的 events CSV |

### 4.2 16 列字段表

```
src_gs_node_id,         # 0  GS 在 ns-3 里的节点 ID
dst_compute_sat_node_id,# 1  目的 C SAT 节点 ID
lambda_req_per_sec,     # 2  回放模式忽略；reader 也跳过 > 0 校验
L_in_mean,              # 3  回放模式忽略
L_in_std,               # 4  回放模式忽略
L_in_min,               # 5  两种模式都 clamp
L_in_max,               # 6  两种模式都 clamp
L_out_mean,             # 7  Compute 应用采样用
L_out_std,              # 8
L_out_min,              # 9
L_out_max,              # 10
bytes_per_token,        # 11
packet_payload,         # 12 旧字段，TCP 用不上
start_time_ns,          # 13 应用启动时间
stop_time_ns,           # 14 clamped 到 simulation_end_time_ns
events_filename         # 15 相对 run_dir 的路径（仅 16-列）
```

### 4.3 合成模式：`workload/schedule.py`

`generate_schedule(config, output_path, *, num_satellites, num_ground_stations, roles_path, dst_strategy="first_compute") → int`：

逻辑：
1. 从 `satellite_roles.txt` 读所有 C SAT ID。
2. 对每个 GS 一行：
   - `src_gs_node = num_satellites + gs_idx`（ns-3 里 GS 节点编号在所有 sat 之后）。
   - `dst_compute` 按 `dst_strategy` 挑。
   - 每 GS 的 λ = `lambda_total / num_gs`。
3. 时间窗口：`start_ns = 500ms`，`stop_ns = duration - 500ms`（前后留 0.5s 给路由 settle 和迟到响应）。

### 4.4 回放模式：`workload/events_replay.py`

`install_events_replay(...)` 关键参数：

```python
install_events_replay(
    config,
    per_gs_dir=Path(".../traffic_generator/real_run/per_gs"),
    run_dir=Path(".../runs/run_xxx"),
    num_satellites=100,
    num_ground_stations=5,            # ← 拓扑里有几个 GS，多余的 trace 文件会被丢掉
    roles_path=Path(".../satellite_roles.txt"),
    dst_strategy="first_compute",
    stage_mode="copy",                # 或 "symlink"
    l_out_mean=200, l_out_std=100,
    l_out_min=1, l_out_max=2000,
    on_log=print,                     # 警告/状态推到这个回调
)
```

逻辑：
1. **扫描** `per_gs_dir` 下所有 `events_gs<N>_*.csv`，建 `{gs_idx: path}`。
2. **裁剪**：如果传了 `num_ground_stations=5`，那么 `gs_idx >= 5` 的文件会被跳过，警告写到 `on_log`。
   - **这是为了防止 trace 有 10 个 GS、但拓扑只有 5 个 GS 时出现"bad src node 105"那种崩溃。**
3. **stage**：把每个 events CSV 拷（或软链）到 `<run_dir>/events/events_gs<N>_*.csv`。
4. **写 schedule**：每个保留下来的 GS 一行 16 列，最后一列指向 stage 后的相对路径。
5. **CRLF 安全**：写 schedule 时用 `lineterminator="\n"`（C++ reader 也会剥 `\r`，双保险）。

## 5. ns-3 主配置文件：`workload/ns3_config.py`

**这一步是什么？** 写 `run_dir/config_ns3.properties`，告诉 ns-3 主程序"该读哪些路径、跑多长、用什么参数"。

## 6. ns-3 C++ LLM 模块：`workload/ns3_module/`

**这一步是什么？** 在 ns-3 仿真器里实际跑 LLM 工作负载的 3 个 application + 1 个 scheduler。仿真过程中边跑边写 CSV。

源码同步到 ns-3 主目录靠 `bash workload/install_ns3_module.sh`（rsync + waf build）。改了 C++ 必须重跑这个脚本。

### 6.1 在线协议：`LLMHeader`

24 字节 little-endian 结构，每个 TCP 流的最前面 24 字节：

```cpp
struct LLMHeader {
    uint64_t t_emit_ns;     // bytes  0..7   GS 端发起请求的纳秒
    uint32_t req_id;        // bytes  8..11  GS 本地的递增计数器
    uint32_t src_node_id;   // bytes 12..15  原始 GS 的 ns-3 节点 ID
    uint32_t L_in;          // bytes 16..19  prompt token 数
    uint32_t reserved;      // bytes 20..23  恒为 0
};
```

GS 写入这 24 字节后，紧跟着发 `L_in × bytes_per_token` 字节的 prompt payload（全 0），然后 `ShutdownSend()`。

### 6.2 `LLMRequestApplication` — GS 端 TCP 客户端

#### TypeId attributes（参数）

| 名字 | 类型 | 默认 | 用途 |
|---|---|---|---|
| `DestAddress` / `DestPort` | Address / uint16 | -- / 9999 | 目的 C SAT 的 IP + 端口 |
| `Lambda` | double | 10.0 | req/s，**只在 synthetic 模式生效** |
| `LInMean / LInStd` | double | 500 / 100 | **synthetic 模式的 Normal 采样** |
| `LInMin / LInMax` | uint32 | 1 / 2000 | clamp，两种模式都生效 |
| `BytesPerToken` | uint32 | 4 | payload 缩放 |
| `ResponseLogFilename` | string | — | 该 GS 的 response CSV 路径 |
| **`EventsFilename`** | string | `""` | **非空就切换到回放模式** |

#### `StartApplication()` 分叉

```cpp
if (m_events_filename.empty()) {
    // 合成模式：构造 Exp + Normal 采样器 → ScheduleNext()
} else {
    // 回放模式：ScheduleEventsFromFile()
}
```

#### 合成模式的循环

`ScheduleNext()` → `Simulator::Schedule(Seconds(指数采样), EmitRequest)` → `EmitRequest()` 采一个 L_in，调用 `EmitRequestWithLIn(L_in)`，再调用 `ScheduleNext()` 形成懒链。

#### 回放模式的批量调度

`ScheduleEventsFromFile()` 一次性把整个 CSV 全部 Schedule 进 ns-3 的事件队列：

```cpp
for each row (req_id, src_gs_idx, t_emit_ns, L_in, L_out) in CSV:
    if t_emit_ns < now: skipped++; continue
    Simulator::Schedule(NanoSeconds(t_emit_ns - now),
                        &LLMRequestApplication::EmitRequestWithLIn,
                        this, clamped_L_in);
```

控制台会看到这样一行总结：
```
> LLMRequest node 100 replay: scheduled=650560 skipped=0 from .../events_gs0_tokyo.csv
```

#### `EmitRequestWithLIn(L_in)` — 两种模式都走这里

每次发起请求时：
1. 分配一个 `ReqConn` 记录（req_id, L_in, t_emit_ns, total_send_bytes = 24 + L_in × bytes/tok, …）。
2. 创建一个新 TCP socket，绑定 4 个回调（Connect、Send、Recv、Close）。
3. `Bind()` + `Connect()` 到目的地。
4. 计数器 `m_tx_pkt_count++`。

#### `PumpSend(sock)` — 发送主循环

- 先发 24 字节 LLMHeader（如果没发过）。
- 再分块（每块最多 65000 字节）把 L_in × bytes_per_token 字节的 prompt 全部发完。
- 全发完调用 `ShutdownSend()` 通知对端 EOF。
- `OnConnectSuccess`、`OnDataSent`（TCP 缓冲腾出空间时）都会调它。

#### `OnRecv(sock)` — 收响应

每次有字节到达，更新：
- `bytes_received` 累加
- `t_first_byte_ns` （第一个字节到达时间）
- `t_last_byte_ns` （每次刷新）

#### `OnClosedNormal(sock)` — 对端 FIN，写日志

写**两行**到 response CSV：
- `response_pkt_id=0`：`t_first_byte_ns`（用来算 TTFT）
- `response_pkt_id=1`：`t_last_byte_ns`（用来算 total）

这样 lifecycle.py 用 `groupby(req_id).min/max` 就能同时还原 TTFT 和 total，不用修改 parser。

L_out 从字节数反推：`L_out_recovered = bytes_received / bytes_per_token`。GS 端不知道 src_compute_sat_id（写 -1），由 lifecycle.py 后期 JOIN 时填回去。

### 6.3 `GatherApplication` — 在 C SAT 收 prompt 的 TCP 服务器

每个 C SAT 装一个，监听端口 9999。

#### 状态机（每个连接）

```
[idle]                           ←  accept(socket)
  ↓ recv first byte
[reading header]    收 24 字节 LLMHeader, 解析出 (t_emit, req_id, src, L_in)
  ↓ 第 25 字节到达
[reading payload]   累计 payload_bytes 到达 L_in × bytes_per_token
  ↓ 收齐
[done]              fire m_gather_complete_cb(sock, hdr,
                          t_first_arrival_ns, t_last_arrival_ns)
                    解除本地 recv 回调（所有权交给 ComputeApplication）
```

每个连接一行日志写到 `llm_gather_node<sat>.csv`：

```
req_id, compute_sat_id, t_first_arrival_ns, t_last_arrival_ns,
D_gather_ns,                      ← = t_last - t_first
total_pkts_expected, total_pkts_received,   ← TCP 下都填 2，是 legacy 字段
src_node_id, L_in, L_out_expected, t_emit_ns
```

如果连接半路挂了（FIN 前 payload 还没收齐），写一行到 `llm_stuck_node<sat>.csv`。

### 6.4 `ComputeApplication` — 在 C SAT 跑推理 + 回响应

每个 C SAT 装一个。**单服务器 FIFO 队列**。

#### TypeId attributes

| 名字 | 默认 | 用途 |
|---|---|---|
| `AlphaNsPerInputToken` | 100k ns | α |
| `BetaNsPerOutputToken` | 50k ns | β |
| `GammaNs` | 10M ns | γ |
| `BytesPerToken` | 4 | 响应 payload 缩放 |
| `LOutMean / LOutStd / LOutMin / LOutMax` | 200 / 50 / 1 / 1000 | Normal 采样 L_out |

#### 生命周期

```
OnGatherComplete(sock, hdr, t_first, t_last):
    L_out = Normal(LOutMean, LOutStd) clamp [LOutMin, LOutMax]
    enqueue(sock, hdr, L_out, t_queue_enter=now)
    if idle: StartNextCompute()

StartNextCompute():
    pop queue front
    T_compute_ns = α·L_in + β·L_out + γ
    t_compute_start = now
    T_queue_wait_ns = now - t_queue_enter
    Simulator::Schedule(T_compute_ns, OnComputeComplete)

OnComputeComplete(slot):
    t_compute_end = now
    写一行到 llm_compute_node<sat>.csv
    SendResponse(slot)
    if queue 非空: StartNextCompute()

SendResponse(slot):
    total_response_bytes = L_out × bytes_per_token
    PumpResponse(sock)  ← 分块发 → 发完 ShutdownSend()
```

#### Compute 日志列

```
req_id, compute_sat_id, src_node_id,
t_queue_enter_ns, t_compute_start_ns, t_compute_end_ns,
T_compute_ns, T_queue_wait_ns,
L_in, L_out
```

### 6.5 `LlmWorkloadScheduler` — 把 schedule.csv 翻译成 application

`LlmWorkloadScheduler::InstallSchedule()` 是真正读 schedule 然后 install application 的地方：

```
for entry in schedule:
    # 校验：src/dst 节点 ID 在拓扑里存在
    if src_gs_node_id >= total_nodes: NS_FATAL_ERROR("bad src node X")

    # 每个 C SAT 装一次 Gather + Compute（用 set 去重）
    if 该 SAT 还没装过:
        install ComputeApplication (alpha/beta/gamma/L_out_dist)
        install GatherApplication (port=9999, log path)
        wire GatherComplete → Compute.OnGatherComplete

    # 每行装一个 RequestApplication 在 src GS 上
    if entry.events_filename.empty():
        # synthetic
        SetAttribute Lambda, LInMean, LInStd
    else:
        # replay
        SetAttribute EventsFilename = run_dir + "/" + entry.events_filename
        （不设 Lambda/LInMean/LInStd，让默认值 0 暴露任何误用）

    install LLMRequestApplication on src GS
```

仿真结束时 `WriteResults()` 把所有 application 的计数器汇总：

```

> tx_request_packets     = 1076

> gather_complete_count  = 878
```

## 7. 路由 / 转发表：fstate 是怎么生效的

很多人在这里被绕晕，所以单独拎出来。

### 7.1 静态视图：每个 fstate_<t>.txt 是什么

文件路径形如：
```
cache/<hash>/state/<network_name>/dynamic_state_1000ms_for_30s/fstate_0.txt
                                                                fstate_1000000000.txt
                                                                fstate_2000000000.txt
                                                                ...
```

每个文件是某个时刻的全局转发表，每行：
```
<from_node>,<to_node>,<dst_node>,<via_iface>
```

意思是"从 from_node 想去 dst_node 时，应该把包丢给 to_node（通过哪个接口）"。

### 7.2 augment_fstate.py 在做什么？

默认 Hypatia 只为 `dst = 每个 GS` 这种目的生成路由（也就是说，从任何节点出发去任何 GS 都有路由）。但**我们的请求方向是 GS → C SAT**——目的地是卫星，不是 GS。

`paper/satellite_networks_state/fstate_augment.py` 干的事情：
- 对每个 C SAT id，**重写**所有 fstate_*.txt，**新增**以这个 C SAT 为 dst_node 的全部转发条目。
- 算法用 Dijkstra（ISL 距离），从每个节点找到去该 C SAT 的最短路径，记录下一跳。
- 在 dynamic state 目录里写一个 `.phase_a_augment.json` manifest，记录"已经为 dst sat id ∈ {2, 12, …} 增强过了"。

`topology/build.py` 会自动对所有 C SAT 跑一次 augment。

### 7.3 当前状态

✅ augment 流程已集成在拓扑生成里，dashboard 看不到这一步（自动跑）。
✅ 已知 bug 修复：早期 augment 只补一个 dst sat，现在 augment **所有 C SAT**。

## 10. 结果分析：`spacesim/analysis/lifecycle.py`

### 10.1 输入

`logs_ns3/` 目录下：
- `llm_gather_node<sat>.csv`（一个 C SAT 一份）
- `llm_compute_node<sat>.csv`（一个 C SAT 一份）
- `llm_response_node<gs>.csv`（一个 GS 一份，**每条完整请求两行**：first-byte 和 last-byte）
- `llm_workload_summary.csv`（每次跑只有一行：tx/gather/compute 计数）

### 10.2 重建流程

`build_lifecycle_df(logs)`：

1. **Response 聚合**：每个 `(req_id, gs_node_id)` 上做 `min/max(t_response_emit_ns, t_response_recv_ns)` → 把 2 行合成 1 行。
   - `t_response_first_recv_ns = min(t_response_recv_ns)`（TTFT 用）
   - `t_response_last_recv_ns = max(t_response_recv_ns)`（total 用）
2. **Inner JOIN** `gather ∪ compute` on `(req_id, compute_sat_id, src_node_id, L_in)`。
   - 这个复合键确保多 GS 场景下 req_id 撞车也能区分（每个 GS 自己从 0 开始计数）。
3. **再 JOIN** 上面的结果和 response 聚合 on `(req_id, src_node_id == gs_node_id)`。
4. **派生列**：
   ```
   T_uplink_ns       = t_first_arrival_ns - t_emit_ns
   D_gather_ns       (已经在 gather 日志里)
   T_queue_wait_ns   (已经在 compute 日志里)
   T_compute_ns      (已经在 compute 日志里)
   T_return_ns       = t_response_last_recv_ns - t_compute_end_ns
   T_TTFT_ns         = t_response_first_recv_ns - t_emit_ns
   T_total_ns        = t_response_last_recv_ns - t_emit_ns
   ```

### 10.3 辅助函数

- `summarise(df)` → `{n, mean_TTFT_ms, p50_TTFT_ms, p99_TTFT_ms, mean_total_ms, p50, p99}`
- `stage_means_ms(df)` → 5 个阶段的均值 (ms)，供堆叠柱状图用
- `enumerate_partial_requests(logs)` → 找在 gather / compute / response 三方中只出现在部分日志的 req_id（被丢的请求）

✅ 完整。多 GS 场景下的复合键 JOIN 已经验证过。
✅ 上次跑出来 220 条完整 lifecycle，TTFT 均值 12.3 s（其中 queue 等待 11.9 s——5 GS 全打 1 个 C SAT 的正常物理结果）。

## 12.5  Trace 截断和"为什么 ns-3 这么快"的真相

这是用户最容易困惑的地方，单拎一节讲清楚。

### 现象

跑一次 dashboard，duration_seconds=30 秒，trace 是 traffic_generator 生成的 24 小时数据。日志显示：

```
LLMRequest node 100 replay: scheduled=186 skipped=0
LLMRequest node 101 replay: scheduled=159 skipped=0
...
tx_request_count = 1076
仿真 30s 用了墙钟 ~10s
```

直觉反应是"什么？trace 有 325 万条事件，怎么只跑了 1076 条？仿真器一定偷工了！"

### 实际发生了什么

**没偷工，是 trace 太长。** 每个 events_gs<N>.csv 里 `t_emit_ns` 范围是 `[0, 86399e9]`（24 小时）。
ns-3 的 `LLMRequestApplication::ScheduleEventsFromFile()` 会把整个 CSV 全部 `Simulator::Schedule()` 进事件队列，但仿真时钟到 `simulation_end_time_ns=30e9` 就停了——剩下 99.97% 的事件**还在队列里**没等到时刻就被切掉了。

```
30s / 86400s = 0.0347% × 总事件 3,253,985 ≈ 1076  ✓
```

数字完全对得上。

### 现在 dashboard 怎么处理

1. **install_events_replay 在 stage 阶段就把 trace 裁剪到 sim 窗口** — 不再把 325 万条事件全 schedule 进 ns-3 队列，只 stage `[offset, offset + duration)` 区间内的事件。
2. **新增 `trace_start_offset_sec` 字段** — 让用户跳到 trace 的任意时刻开始仿真。例如设 50400（= 14:00 UTC）就能仿真"下午高峰那 30 秒"。
3. **侧栏新增 fit check** — 在你点 Run 之前就显示：

   ```
   Trace covers ~24.0h. Sim window will fire 1,076 of 3,253,985
   events (0.033%), avg 35.9 req/s across 5 GS.
   ```

   - 如果你的 sim 窗口落在 trace 之外（offset 太大），直接弹红 error。
   - 如果触发比例 < 5%，弹黄 warning 提示"trace 大部分被忽略，要么加长 duration 要么缩短 trace"。

### 当前 ns-3 在 30s 仿真做的真实工作量（实测）

| 指标 | 值 |
|---|---:|
| 触发的请求数 | 1076 |
| 完成 gather (TCP 上行结束) | 879 |
| 完成 compute (推理 + 回响应) | 783 |
| 上行 payload 实际字节 | 3.65 MB |
| 上行等效吞吐 | 2.9 Mbit/s（链路上限 10 Mbit/s）|
| T_uplink p50 | 213 ms（多跳 GSL+ISL，物理合理） |
| D_gather p50 | 2.6 ms（TCP MSS 分段累积时间） |
| 墙钟耗时 | ~10 s |

T_uplink 和 D_gather 都是**真实分布**——如果偷工，它们应该是 0 或固定值。所以 ns-3 确实在跑包级仿真，10 秒墙钟跑 30 秒仿真在这个事件规模下是合理的（每秒 ~10 万个 ns-3 事件）。

### 取舍：为什么不让 sim 跑完整个 24h trace？

包级 ns-3 跑 30s 仿真 → ~10s 墙钟。线性外推：

```
24h sim ≈ 86400 × (10/30) ≈ 28800 s 墙钟 ≈ 8 小时
```

而且这是**线性下界**——实际队列爆炸时事件数还会 super-linear。所以"跑完一整天的真实负载"在包级仿真里物理上不可行。正确的做法：

- 选 trace 的一个**有代表性的小窗口**（比如下午高峰 30s、夜间低谷 30s）
- 用 `trace_start_offset_sec` 跳到那个窗口
- 把"24h 平均"留给排队论或流体模型，不要让 ns-3 做这种活儿

## 17. 术语表

| 术语 | 中文/含义 |
|---|---|
| **C / T** | Compute / Transit。卫星角色，决定它是不是接收请求做推理的目的地 |
| **GSL / ISL** | Ground-Sat Link / Inter-Sat Link，地星链路 / 星间链路 |
| **fstate** | forwarding state，某时刻全网转发表的快照 |
| **augment** | 给 fstate 补充以 C SAT 为目的地的路由条目 |
| **TTFT** | Time-To-First-Token：`t_response_first_recv_ns - t_emit_ns` |
| **T_total** | 端到端延迟：`t_response_last_recv_ns - t_emit_ns` |
| **D_gather** | 在 SAT 端 prompt 完整接收的 TCP framing 时间 |
| **T_queue_wait** | compute SAT 队列等待时间 |
| **T_compute** | α·L_in + β·L_out + γ，模型推理本身的时间 |
| **L_in / L_out** | prompt token 数 / response token 数 |
| **req_id** | GS 本地的请求编号；和 `src_node_id` 一起组合成全局唯一 |
| **NHPP** | 非齐次 Poisson 过程，请求到达率随时间变化的 Poisson 过程 |
| **thinning** | Lewis-Shedler 算法：用大速率 Poisson 候选+概率筛选生成 NHPP 事件 |
| **synthetic / trace_replay** | 两种工作负载来源：仿真器内现采 / 读 events CSV 回放 |
